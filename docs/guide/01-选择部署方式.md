# 选择部署方式

本项目有三种部署方式，按推荐程度从高到低排列。

## 对比

| 维度 | 服务器 Docker | 云函数 | GitHub Action |
| --- | --- | --- | --- |
| 推荐度 | ⭐ 最推荐 | 可用性待验证 | 已过时 |
| 成本 | 需自备服务器 | 少量付费 | 免费 |
| 出口 IP | 固定 | 固定（同地域） | 每次漂移 |
| 登录态稳定性 | 稳 | 待验证 | 易掉 |
| 上手难度 | 中 | 较高 | 低 |

## 1. 服务器 Docker（最推荐）

有服务器（或 NAS、支持 Docker 的设备）就选这个。出口 IP 固定，「抓 Cookie 的出口」和「跑任务的出口」天然一致，登录态最稳。

部署见 [服务器 Docker](deploy/docker.md)。

## 2. 云函数

没有服务器、愿意少量付费时可选。通过阿里云函数计算（FC）部署，任务函数和 gost 隧道函数跑在同一地域，保证出口 IP 一致。

⚠️ 该方式**目前还未经过测试，可用性未知**，适合有动手能力、愿意折腾的用户先行验证。

部署见 [云函数](deploy/fc.md)。

## 3. GitHub Action（过时）

免费、无需服务器，但存在两个固有问题：

1. **GitHub 严格的 Action 审查**：公共仓库的定时任务容易被限制。要绕过，需要把代码 clone 到本地、创建新的私有仓库、再把代码推上去。
2. **出口 IP 每次运行都变**：抖音会校验登录 Cookie 的出口 IP，IP 一变登录态就掉。所以必须额外配一个固定出口的 HTTP 代理，写进 `.env` 的 `PROXY_ADDRESS`。

关于 IP 与登录态的关系，见 [Cookie 与出口 IP](guide/02-cookie与出口IP.md)。

部署见 [GitHub Action](deploy/action.md)。
